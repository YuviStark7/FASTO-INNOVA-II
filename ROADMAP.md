### Requested directly by Yuvi — 2026-08-27 (not from the queue)

**R4. [S] Sharp backdrops, and a cross-fade between them.** Three things. (1) **The blur was resolution, not compression.** The rotating photos were 2048×857 while `hero-farm.png` beside them was 2939×1690, so on a 3440-wide monitor the backdrops were being stretched about 1.7× and nothing else was — which is what made them look soft. Yuvi supplied his own 3440×1440 copies; they arrived as `Background 1.jpg`…`Background 6.jpg`, which is not what the app loads, so they were copied byte-for-byte onto `bg-1.jpg`…`bg-6.jpg` with no re-encoding. The duplicates are in `.gitignore` and safe to delete. (2) **`hero-farm.png` → `hero-farm.jpg`**, same dimensions, 758 KB instead of 4.94 MB, mean per-pixel difference about 1/255. It is not only the split-second fallback behind the app shell — it is also the sign-in background — but it sits under a `rgba(10,6,6,.55)`→`.8` gradient in both places, so the compression is not visible. (3) **The photo now cross-fades over 900ms** instead of cutting, using two stacked layers in `#main`.

**This shipped broken the first time and had to be fixed the same day — worth reading if you ever touch this code.** Three separate mistakes, all of which a passing test suite failed to notice: (a) each incoming layer was given an ever-climbing z-index, which passed the scrim on the third swap and the topbar and screens on the fourth, so the backdrop covered the entire dashboard; (b) the outgoing layer was never hidden after its fade, so from the third swap onwards the "spare" layer was still fully opaque and the new photo appeared instantly — one fade, then cuts forever; (c) fixing those introduced a third: an edit left a stray comment-close marker between two CSS rules, and the browser silently swallowed the `.backdrop-layer` rule that followed it, so `opacity:0` never applied and the fade stopped happening altogether, with nothing reporting an error. **The root cause behind all three was the verification, not the code** — the original 23 checks drove a hand-written fake DOM with no real opacity, no real stacking and no real stylesheet, so they confirmed the code did what it was written to do rather than what a browser does with it.

*What is in place now so this cannot repeat quietly:* the two layers own z-index 0 and 1 and never move between them (two layers only ever need two values); the outgoing layer is hidden on a timer once the new photo is opaque, which is what frees it for reuse; and `settleBackdrop()` ends any fade still running before a new one starts, since you can leave and return to the Dashboard faster than 900ms. `qa_check.js` gained four dependency-free guards — CSS comment markers balanced and none stray, braces balanced, the backdrop stacking order (layers 0/1 < scrim 2 < content 3) read from *comment-stripped* CSS so a rule swallowed by a runaway comment reads as missing, and the fade length in the CSS matching `BACKDROP_FADE_MS` in the JS. New optional `test_backdrop.js` (39 checks) drives the real `showBackdrop`/`rotateBackdrop` against the real stylesheet in jsdom and reads back *computed* opacity and z-index, so the cascade decides the answers; it needs `npm install jsdom` once and skips cleanly with a message if that is missing. Re-introducing each bug one at a time fails it by 9, 18 and 20 checks respectively, and two of the three also fail `qa_check.js`. *What still needs eyes:* jsdom has no transitions, so it only sees the state either side of a swap, never the dissolve itself — the mid-fade frame was checked separately in a real browser. Files: `js/app.js`, `css/app.css`, `index.html`, `qa_check.js`, `test_backdrop.js` (new), `assets/hero-farm.jpg` (new), `assets/Backgrounds/bg-1…6.jpg`, `.gitignore`.

12. **[M] Export Research Progress + outreach log (CSV/PDF).** — shipped 2026-09-03. An **Export** button now sits beside "See all" on the Dashboard. It opens a sheet with three choices: the Research Progress table as a CSV, the outreach log as a CSV, or both together as a printed report your browser can save as a PDF. Until today the only way to get anything out of this app for the internship write-up was to retype it off the screen — and the screen deliberately shows less than it knows.

***The judgement call the whole thing rests on: a row in the research export is one PRODUCT, not one conversation.*** The Dashboard shows one row per conversation carrying that farm's *largest* product and silently hides the rest, which is right for a glance and wrong for a document. A farmer offering tomatoes, courgettes and olive oil appears once on screen, and if the export copied that, the quantities in a report would not add up to what was actually pledged. So three products is three rows, with the conversation repeated — and the sheet, the CSV and the printed report all **say so in words**, the same rule the Admin funnel follows: state the unit rather than let the reader work it out. A conversation whose profile was captured with no products at all still gets its row, with the product columns blank; it is the interesting case, not a case to drop.

*Four more decisions worth knowing:*

**(a) The CSV separator follows the language the app is set to, and so do the decimals.** Excel splits a file on the list separator of its *own* locale: an Italian copy opens a comma-separated file as a single column of text, and reads `3.00` as three hundred. So Italian gets `;` with `3,00` and English gets `,` with `3.00`, and the sheet states which one it is about to use. This is the one place where the language changes what *leaves* the app — the logistics email deliberately keeps English field names because the partner reads every farmer's, but this file is read by whoever pressed the button.

**(b) Every price column says it is an assumption.** `PRICE_ASSUMPTIONS` is desk research you can override by clicking a price, not a figure a buyer has agreed to. The column is headed "Price assumption (EUR/kg)", the money column is "Estimated weekly value (EUR, from the assumption)", and the printed report repeats it in the footer. An unlabelled "weekly value" column in a document handed to a tutor is the same mistake as presenting an invented buyer reply as real, which this app has a standing rule against.

**(c) The PDF is your browser's, not a library's.** No build step here and no bundler, so a PDF library would mean a CDN script downloaded on every visit for a button most sessions never press. Instead a `@media print` block hides every other child of `<body>` and prints a plain black-on-white report — which also means no popup window for a blocker to eat. Press **Print / PDF** and choose "Save as PDF" as the destination. The rule is written as `body > *` rather than a list of ids on purpose: a fifth sheet added next year would otherwise print itself across the report.

**(d) A cell that starts like a formula is neutralised.** Product names and follow-up notes are typed by the farmer, and a spreadsheet runs a cell beginning `=` `+` `-` `@` as a formula when the file is opened. Quoting does not stop that; a leading apostrophe does. Plain negative numbers are left alone.

*Smaller things:* the button is on the Dashboard rather than in the top bar, because the top bar is already tight with a long farm name (item 10) and the Dashboard is the reporting screen; the export sheet is the fourth body-level sheet and goes through the same `openSheet`/`closeSheet` machinery as the other three, so focus, Tab and Escape behave identically; with nothing to export the buttons are disabled and pressing them anyway says so rather than downloading an empty file; a draft whose conversation is missing is exported and *named* as such rather than dropped; and only `status === "sent"` counts as sent, never "not draft", since `createOutreach` can leave that column null.

11. **[M] Accessibility pass.** — shipped 2026-09-02. **Before today the app could not be used without a mouse at all.** The sidebar, the conversation history rail, the client list, the three example chips and the two clickable cells on the Dashboard were all plain `div`s and `span`s with a click handler on them. A click handler is the only thing that makes those react, and Tab never stops on one — so a farmer using a keyboard, or a screen reader, or a switch, could sign in and then reach nothing but the message box. They are all real buttons now, and everything that was carried only by a colour is carried by a name as well.

***The judgement call the whole thing rests on: the boot lock is stronger than it looks, and making things focusable nearly broke it.*** While the app is loading, `css/app.css` puts `pointer-events:none` on the nav, the top bar and the search box. That stops a mouse. It does nothing whatsoever to a keyboard — a focusable element with `pointer-events:none` still takes Tab and still fires on Enter. It didn't matter while the nav items were divs, because a div was never focusable in the first place; the moment they became buttons, the lock had a hole in it, and pressing one mid-load would have started a chat that `loadFarmerData()` wipes out a second later, which is the exact bug item 4 existed to prevent. So the same controls the stylesheet dims are now genuinely `disabled` (`setBootLock()` in `js/app.js`), and there is a note at that list saying anything added to the `#app.booting` CSS rules belongs in it too.

*What changed, in four groups:*

**(a) Keyboard.** Everything listed above is a button. The current screen, the open conversation and the open draft are marked with `aria-current`, so which one you are on is not only a background tint. There is a skip link — the first thing Tab reaches, invisible until then — because otherwise every screen change costs four presses through the sidebar. The sidebar is a `<nav>` landmark and the app body a `<main>`, which is the fastest way for a screen-reader user to jump between them.

**(b) The three sheets are now real dialogs.** They were `display:none` overlays and nothing more. Opening one left focus on the button underneath it, so you pressed Enter and then had to Tab through the entire app behind the panel to reach the thing you had just opened — and could Tab straight back out the far side while it was still up. Now focus moves onto the close button when a sheet opens, Tab is held inside it, the app behind is hidden from assistive tech and inert, and closing puts focus back on the exact button that opened it. **This fixed a real bug on the way past:** each sheet had its own Escape handler, all three listening at once, so a single press while correcting a profile also closed the match sheet waiting behind it. Escape now closes the top one only. Focus also survives the awkward case — saving a profile redraws the Dashboard, the chat rail and the client list, so the button that opened the sheet may not exist any more; if it has gone, focus is left alone rather than being thrown to the top of the document.

**(c) Names.** Every icon-only button — the bell, the avatar, attach, send, the truck, the three close buttons, the "Not saved" chip — carries an `aria-label`, and so do the search box and the message box, which had a placeholder and nothing else. A `title` was not enough: it needs a pointer to appear at all, and it is only a fallback name that some screen readers skip. All of them go through the dictionary, so they are Italian in Italian; a label frozen in English is one of the regressions tested for below. Table headers declare their scope, the toast is a live region (until now every toast in this app — a failed save, a Guardian correction, a stale draft — was purely visual), and the error banners are alerts.

**(d) Contrast, measured against your actual photos rather than guessed at.** The six backdrops in `assets/Backgrounds` were sampled directly, taking the brightest 99.9th-percentile pixel in the band each surface sits over and putting it through the app's own scrim. **The top bar was the worst of it: it sits where the scrim is weakest — it fades from 5% at the top of the photo to 65% at the bottom — and where a farm photo is most likely to be sky. Over a bright sky the glass left it at rgb(129,129,127), which puts the farmer's own name, in solid white, at 3.91:1, and the search placeholder at 2.15:1.** The top bar now has a heavier tint of its own (white 9.8:1), which leaves the photo untouched everywhere else — the alternative, darkening the top of the scrim, would have dimmed the hero image for everyone. Alongside it: `--ink-70` and `--ink-50` moved to .78 and .62, since at .50 every secondary label in the app — table headers, `.foot`, percentages, hints, placeholders, all of them 10.5–12px — measured 4.04:1 on a panel; the inactive sidebar labels went from 55% to 72% opacity (3.47 → 4.91, and the active item is still unmistakable because it also carries its own background); the "Not saved" chip took the brighter amber this app already uses for text on a tint (3.46 → 4.73); and `pill-blue` moved one shade (4.50, a hair under).

**Verified** with a scratch jsdom + postcss harness of **124 checks** driving the real page with the real stylesheets — clicking the actual buttons, reading back where focus actually went, and computing real contrast ratios from the resolved CSS tokens against the measured photo values. Run against the **unmodified** build as a control it passes only 18 and fails 64, and the 18 that pass are almost all the "layout hasn't moved" guards, which is the point of having them. **Proof the checks aren't passing for free: 72 realistic regressions were put back one at a time — every control type reverted to a div, the skip link removed, the focus ring removed and then quietly weakened to a hairline, each `aria-current`/`aria-pressed` dropped, each live region dropped, the dialogs de-modalled, focus not moved in, focus not restored, Tab allowed out the back, Shift+Tab wrapping the wrong way, Escape closing everything again, the boot lock switched off, and every one of the contrast tokens dialled back to where it was — and all 72 were caught.** **55 of those 72 are caught by `qa_check.js` alone**, which is what matters after today, since it needs no install and runs on every future daily pass: it now refuses a click handler on anything a keyboard can't reach, a button with no accessible name, an `aria-labelledby` pointing at nothing, a sheet that has stopped being a dialog, a missing focus ring or boot lock, and it recomputes all eight contrast ratios from the CSS on every run. `test_engine.js` 19/19, `test_data_layer.js` 203/203, `test_backdrop.js` 39/39, `qa_check.js` PASS.

***What still wants your eyes — and one thing I deliberately did not change.*** This ran unattended, so there is **no rendered screenshot behind it**; jsdom decides which rule wins and what it resolves to, but it has no layout engine. Two things to glance at: the top bar, which is now noticeably darker than the panels below it (that is the fix, but you should like it), and the sidebar, where the inactive items are brighter than before.

**The Fasto-AI screen still fails contrast and I have left it alone on purpose.** Everything on that screen sits directly on the photo with only a light glass over it, and the numbers are bad: Fasto's own replies (`.bubble.in`, white text on a 14% white bubble) come out at **2.43:1** over a bright backdrop, the conversation rail at 3.15, the example chips at 3.39, the message bar at 4.00. Your own messages are fine — they are solid brand red at 8.1:1. Fixing it means changing the colour of surfaces you designed in Figma, which is a look decision rather than a mechanical one, and it is exactly the kind of change the backdrop episode says not to ship on a headless approximation with nobody looking. Three options, in the order I'd rank them: (1) make those four surfaces black glass like the rest of the app instead of white — arguably *more* faithful to the "translucent black glass" identity, and it fixes all four at once; (2) make the incoming bubble a nearly-opaque white with dark text, which keeps it light but stops it being glass; (3) deepen the scrim across the middle of the photo, which fixes everything but dims the hero image. Say which and it is a small, contained change. *Other known limitations:* the `inert` attribute behind an open sheet is ignored by older browsers, where the focus trap is what holds the line; and Windows high-contrast mode gets the system focus ring but has had no other attention. 10. **[M] Bilingual UI chrome (IT/EN toggle).** — shipped 2026-08-31. There is now an **IT / EN** switch on the sign-in card and, once you are inside, in the top bar on the right. Press it and the whole app changes language on the spot — nav, tables, buttons, tooltips, placeholders, every toast, all three sheets, and `<html lang>` with them. **The app opens in whatever language the browser is set to** (an Italian phone gets Italian without anyone deciding to force it on the tutors and reviewers who aren't on one) and remembers the choice on that device afterwards. Until today, Brain 1 answered a farmer in Italian inside a screen that said Dashboard, Quantity pledged and Mark as sent.

***The judgement call the whole thing rests on: a language is a display choice, and switching it must never change a single thing stored about the farm.*** The category dropdown reads "tomatoes" in English and "pomodori" in Italian, but the value written to the products table is `pomodori` either way, because that is the word the engine and the database agree on — and in Italian the label happens to *be* the key, so a version that wrongly stored labels would look perfectly correct in Italian and only corrupt a row for an English-speaking farmer. The same applies to the organic dropdown (`yes`/`partial`/`no`), and to chat titles, which are stored: a chat named in one language keeps that wording, rather than the app rewriting database rows because someone changed a display preference.

*Four more decisions worth knowing:*

**(a) What is deliberately NOT translated, and why it isn't an oversight.** The rule is that the app translates its own words, and the offline stand-in does whatever the real Brain would have done. Brain 1's own instructions say *mirror the user's language*, so the scripted offline interview **does** follow the switch — that was the one place the promise was broken. Brain 2 has no such promise: its written notes come from the buyer database, and its **outreach draft is deliberately an Italian message plus an English translation**, which is the one thing a real buyer ever reads. Translating "the English translation" into Italian would destroy the point of having both, so all of it is left exactly as composed.

**(b) The logistics email keeps its English field names.** Only the values follow the farmer. That email is not read by the farmer at all — it is a report to the partner, who receives requests from every farmer on the platform, and an inbox where "Pickup address" is sometimes "Indirizzo di ritiro" is harder to read, not easier. It now carries a **"Farmer's app language"** line instead, so the partner knows which language to answer in.

**(c) `js/core.js` was not touched.** The engine's scoring reasons and the Guardian's corrections are English sentences built inside the file that `test_engine.js` pins at 19/19 and that has been carried byte-for-byte since v0.2 — and they are shown to the farmer, as the reason chips in the "Why these buyers?" sheet and as the amber *"Fasto adjusted one thing on the way through"* notice. They are recognised and rewritten at the boundary instead. That arrangement is exactly the kind that rots silently, so **`qa_check.js` now reads every sentence `core.js` can produce and fails if one of them isn't claimed by a translation pattern** — change a word in the engine and the check says so, rather than the Italian UI quietly reverting to English. When a sentence genuinely isn't recognised it falls through unchanged: an English chip is a blemish, a blank one is a bug.

**(d) The switch lives in the top bar, not the sidebar.** On a phone `.side-bottom` is hidden and the sidebar collapses to a row of icons, so the top bar is the only place reachable on every screen *and* on a phone. It is switched off while the shell is still loading, like the search box and the icon buttons, because `loadFarmerData()` replaces `state.chats` wholesale and a re-render mid-boot would swap the skeleton for an empty table moments before the real one arrived. And it is deliberately *unreachable* while any of the three sheets is open — they are `fixed; inset:0` at z-index 120/130/140, above the bar — so a half-typed logistics request or a half-corrected profile can never be re-rendered out from under you. That is stacking, not a special case in the code.
